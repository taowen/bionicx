# Host-GPU GLX path

## Scope

The controlled client is a genuine AArch64 glibc executable linked against
Xlib and a pinned build of Winlator's Gladio `libGL`. It creates a GLX window,
uses legacy desktop GL calls, reads known pixels back, and swaps into BionicX's
embedded X server. No Termux, proot, root, Mesa software renderer, or Frida is
involved.

Pinned Gladio revision:
`116c0d14dedbea3bd057f98f1db138bb1efe225e`, archive SHA-256
`d275a1e745d2d9388fe37061c379f5872820057a5b43f8bbc34d63c6c70c7024`.

## Failures isolated

Gladio encoded Winlator's fixed GLX major opcode. BionicX assigned GLX opcode
147 rather than 150, so context requests were rejected. The retained upstream
patch discovers the server opcode with `XQueryExtension`.

The first successful GPU run returned the expected pixels from Qualcomm but
the Android screenshot remained black. Instrumentation showed the guest EGL
context was created with `EGL_NO_CONTEXT` before `GLSurfaceView.onSurfaceCreated`
published the compositor context. Its texture was valid on the Gladio worker
thread and invalid in the Android compositor context.

The GLX renderer now owns a JNI setter for its share context. First guest
context creation waits up to five seconds for the Android rendering surface,
then creates the guest context in that share group. This also avoids using a
mutable EGL handle indirectly through another JNI shared object.

BXTEST PASS host-gl-pixels center=242,26,13,255 corner=13,38,191,255
BXTEST PASS glx-present glError=0x0

The screenshot pixel assertion is essential: the first six client-side checks
also passed during the broken, non-shared run. It verifies that the GPU result
reached the final Android framebuffer through the X window texture.

This proves Winlator's translated GLX/host-GLES route. Native Mesa
DRI3/Present with `AHardwareBuffer`/`EGLImageKHR` is a separate route and remains
future controlled coverage.
