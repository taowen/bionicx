# Stateful XRender 0.1 support

## Observed gap

The real `libXrender` client in `x11-desktop-probe` initially reported
`extension-missing`. Merely returning a successful `QueryExtension` reply would
not be sufficient: `XRenderFindVisualFormat` immediately parses the complete
format/screen/depth/visual hierarchy, and drawing uses server-side Picture IDs.

## Implemented protocol boundary

`XRenderExtension` advertises protocol 0.1 and implements the requests exercised
by the controlled client:

- `QueryVersion`;
- `QueryPictFormats`, including ARGB32 and A1 direct formats and a mapping from
  the root visual to ARGB32;
- `CreatePicture` and `FreePicture`, with per-client cleanup;
- `FillRectangles` for `PictOpSrc`.

The extension deliberately reports 0.1 rather than claiming the current Render
version. Composite operators, transforms, filters, gradients, glyph sets and
the newer protocol requests remain future integration-test targets. Picture
attributes are consumed according to their value mask but are not yet applied.

The rectangle decoder uses `XClient.getRemainingRequestLength()` rather than
the socket's available-byte count. This is essential when Xlib pipelines the
next request in the same read buffer.

## Device proof

On x300 (`01408BH601027129`), the rebuilt APK ran the glibc client through the
ordinary untraced executor. The client negotiated Render 0.1, created a Picture,
filled a cyan rectangle, synchronized, and used core `GetImage` to prove the
pixel was nonzero:

```text
BXTEST PASS xrender      version=0.1 event=0 error=0
BXSUMMARY desktop-x11 passed=1 failed=4 xerrors=0
```

The full log is in `evidence/x11-desktop-probe-xrender.log`; the visible fill
and `1/5 strict pass` status are captured in
`evidence/x11-desktop-probe-xrender.png`.
